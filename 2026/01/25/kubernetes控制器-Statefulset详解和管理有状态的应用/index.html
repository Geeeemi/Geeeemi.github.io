kubernetes控制器-Statefulset详解和管理有状态的应用

1、StatefulSet控制器：概念、原理解读

​ StatefulSet 是 Kubernetes 中用于管理有状态应用的一种控制器，核心目标是在容器化和动态调度的环境下，为应用提供“稳定性”和“可预期性”。与 Deployment 不同，StatefulSet 为每个 Pod 分配固定且唯一的身份，并在 Pod 重建后保持不变，从而满足有状态应用对网络标识、启动顺序和数据持久性的要求。StatefulSet 管理的每个 Pod 都具有唯一的名称（如 pod-0、pod-1），并且对应稳定的 DNS 名称，使其他组件可以通过固定名称访问指定实例，而无需关心 Pod IP 的变化。同时，StatefulSet 支持有序创建、有序删除和有序扩缩容，确保 Pod 按照定义顺序逐个启动或终止，这对于主从架构或存在依赖关系的应用尤为重要。

​ 在存储方面，StatefulSet 通常与 PVC 结合使用，为每个 Pod 绑定独立的持久化卷，即使 Pod 被删除并重新创建，原有数据仍然能够保留，从而保证业务状态不丢失。

什么是有状态服务？

​ 所谓有状态服务，是指服务在运行过程中需要保存并依赖状态信息的服务，这些状态通常跨多个请求存在。例如电商系统中的购物车、订单流程，或聊天系统中的会话记录和消息历史，都依赖之前产生的数据状态。与之相对的无状态服务则不会保存任何上下文信息，每个请求都是独立处理的。有状态服务的实现方式通常包括将状态存储在会话中、数据库中，或借助分布式一致性组件（如 ZooKeeper、etcd、Consul）进行统一管理。

​ 会话保持（Session Affinity / Sticky Session） 是指在一段时间内，将同一个客户端的请求持续地转发到同一个后端服务实例上。其目的是保证有状态数据的一致性，避免因为请求被负载均衡到不同实例而导致会话丢失或状态不一致。在 Kubernetes 中，会话保持通常通过 Service 的 sessionAffinity=ClientIP 实现，即基于客户端 IP 将请求固定转发到同一个 Pod。这种机制常用于未将会话状态外置（如存储在 Redis 或数据库中）的应用场景，但在大规模、高可用架构中，通常更推荐将状态外部化，从而减少对会话保持的依赖。

解释StatefulSet 资源中常见字段

这是 StatefulSet 资源中常见字段的完整解释（偏生产理解）。

首先一个前提：
StatefulSet 主要用于 有状态应用，比如 MySQL、Redis、ZooKeeper 等，核心特点是：

  • Pod 名字固定、有序（如 mysql-0、mysql-1）
  • 每个 Pod 有独立、稳定的存储
  • 网络标识稳定（结合 Headless Service）

podManagementPolicy：Pod 的管理策略

作用：控制 Pod 的创建、删除顺序。

常见取值：

  • OrderedReady（默认）
    • 按顺序创建 Pod（0 → 1 → 2）
    • 前一个 Pod Ready 后，才创建下一个
    • 删除时反向顺序
    • 适合数据库、主从架构
  • Parallel
    • Pod 同时创建、同时删除
    • 启动快，但不保证顺序
    • 适合对启动顺序不敏感的应用

replicas：副本数

作用：定义 StatefulSet 中 Pod 的数量。

StatefulSet 中副本是有编号、有顺序的，不是普通 Deployment 那种随机 Pod。

revisionHistoryLimit：历史版本保留数

作用：控制 StatefulSet 更新时保留多少个历史版本。

关键点（很重要）：

  • 否则 StatefulSet 无法正确管理 Pod

    • clusterIP: None

template：Pod 模板（非常关键）

作用：定义 StatefulSet 创建出来的 Pod 长什么样。

里面和 Pod 定义几乎一模一样，包括：

  • labels
  • containers

  • env
  • volumeMounts
  • serviceAccountName（如果需要 SA）

理解方式：StatefulSet = 用这个 template，不断复制 Pod，但给它们不同的名字和存储

updateStrategy：更新策略

作用：定义 StatefulSet 如何滚动更新 Pod。

常见类型：

  • RollingUpdate（默认）
    • 按 Pod 序号倒序更新（先 xxx-2，再 xxx-1，再 xxx-0）
    • 保证有序、可控
  • OnDelete
    • 不自动更新
    • 只有你手动删除 Pod，才会创建新版本

生产环境数据库常见：

  • 非常保守：OnDelete
  • 可控升级：RollingUpdate

volumeClaimTemplates：存储卷申请模板（StatefulSet 的灵魂）

作用：为 每一个 Pod 单独创建 PVC。

关键点：

  • 每个 Pod 都会生成一个独立 PVC
  • PVC 名字带 Pod 编号
  • 删除 Pod，不会删除 PVC（默认）

  • mysql-0 → data-mysql-0
  • mysql-1 → data-mysql-1

风险：

  • 删除 PVC
  • 同时删除 PV
  • 后端真实存储数据直接没了

生产建议：

  • 删除 PVC
  • PV 和真实存储数据仍然保留
  • 可人工恢复

StatefulSet 通过

  • serviceName 保证网络稳定
  • volumeClaimTemplates 保证存储独立
  • podManagementPolicy 和 updateStrategy 保证有序管理
  • template 定义 Pod 具体内容

专门用于 有状态应用的可靠部署。

备注

有 IP 的 Service（如 ClusterIP、NodePort、LoadBalancer）在 DNS 解析后会得到一个固定的虚拟 IP，请求可以直接发送到该 Service IP，由 kube-proxy 在节点上完成转发和负载均衡。由于客户端只需要解析一次 Service 名称即可得到 IP，后续通信不需要再关心后端 Pod 的变化，整体访问路径稳定，使用方式简单，适合对外提供统一访问入口，或者需要通过 Service IP 进行访问和管理的场景。

没有 IP 的 Service（Headless Service，clusterIP: None）在 DNS 解析时不会返回一个统一的虚拟 IP，而是直接返回后端 Pod 的 IP 列表。客户端需要自行从这些 Pod IP 中选择目标进行访问，负载均衡通常由客户端或上层应用实现。相比普通 Service，这种方式 DNS 返回的信息更多，解析和连接逻辑更复杂，但它可以精确感知每个 Pod 的真实地址，非常适合有状态服务使用，例如 StatefulSet 中的数据库、消息队列等场景，用于实现固定身份、主从区分或点对点通信。

简单总结：有 IP 的 Service 适合无状态服务和统一入口访问，强调稳定和易用；没有 IP 的 Service 适合有状态服务，强调直连 Pod 和身份可识别性，而不是性能本身的高低。

5、实战：k8s配置管理中心ConfigMap(简单用法)

ConfigMap概述

ConfigMap 是 Kubernetes 中的一种资源，用于将应用程序的配置数据与容器镜像解耦，从而实现配置的集中管理和动态更新。通过使用 ConfigMap，可以在不重新构建镜像、也不重新部署应用程序的情况下修改配置内容，显著提升应用的可配置性和可维护性。以 Web 应用为例，数据库连接地址、日志级别、功能开关等参数在传统部署方式中往往被硬编码在代码或镜像中，而借助 ConfigMap，可以将这些配置独立出来，在运行时注入到 Pod 中进行使用。这样既避免了因修改配置而频繁构建镜像的问题，也更符合云原生环境下配置与应用分离的设计原则。

ConfigMap配置管理与应用配置注入操作（使用案例5）

当 ConfigMap 以文件形式挂载到 Pod 中时，其配置数据会被映射到容器内的指定路径（例如 /app/config），应用程序只需要从该目录读取配置文件即可使用这些配置。当需要修改配置时，只需更新 ConfigMap 的内容，而无需重新构建镜像或重新部署应用。例如，可以通过 kubectl edit configmap myapp-config 将日志级别修改为 “debug”。在大多数场景下，Pod 内的应用程序可以自动感知到 ConfigMap 内容的变化，并加载新的配置，无需重启 Pod。通过这种方式，ConfigMap 实现了配置的动态管理，使得在不影响业务运行的情况下更新配置成为可能。这种机制在区分开发、测试、生产等不同环境配置，以及在自动化部署流程中进行配置管理时，具有非常高的实用价值。
