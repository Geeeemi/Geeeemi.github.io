k8s持久化存储-常见的存储卷介绍

发表于2026-01-25|更新于2026-01-25|Kubernetes 存储方案
|总字数:10.1k|阅读时长:39分钟|浏览量:

前置

在 Kubernetes 中，数据持久化是解决容器临时性存储问题的关键。默认情况下，容器中的数据存储在容器的文件系统内，但容器的生命周期是短暂的，因此，当容器被删除或重启时，数据会丢失。这种情况对于许多应用程序（特别是数据库应用）来说是不可接受的，因此需要实现数据持久化，将数据保存在持久化存储设备（如磁盘）上，以确保数据在容器的生命周期之外仍然可用。

数据持久化的场景包括：

  • 数据存储：许多应用程序需要保存用户生成的数据，如文件、图片、日志等。通过数据持久化可以确保这些数据在容器销毁或重启后仍然存在。
  • 数据共享：在某些情况下，多个容器或Pod可能需要访问和共享相同的数据。通过将数据存储在持久化卷中，可以使多个容器之间共享数据，实现数据一致性和共享访问。
  • 数据备份和恢复：持久化存储解决方案通常提供数据备份和恢复机制，以防止数据丢失。这对于保护重要数据、应对故障或恢复到先前的状态非常重要。
  • 数据迁移和扩展：在Kubernetes集群中，可能需要扩展应用程序到多个节点或迁移到其他集群。通过将数据存储在持久化卷中，可以方便地将数据与应用程序一起迁移到新的环境，无需担心数据丢失。
  • 数据安全：某些行业或应用程序对数据的安全性有严格的要求。持久化存储解决方案通常提供数据加密和访问控制动能，以确保数据在传输和存储过程中的安全性。

数据持久化是 Kubernetes 中非常重要的组成部分，特别是在涉及到有状态应用（如数据库）时。通过使用 Kubernetes 提供的**持久化卷（Persistent Volumes, PV）和持久化卷声明（Persistent Volume Claims, PVC）**机制，可以有效地管理和持久化容器中的数据，确保数据不随容器的生命周期消失，从而保障应用的高可用性、可恢复性及数据安全。

1、 实战：k8s持久化存储方案-EmptyDir

在 Kubernetes 中，卷（Volume） 是用来提供持久化存储或共享存储的机制。Kubernetes 提供了多种类型的卷，每种卷都有不同的特性和适用场景。以下是一些常用的卷类型及其说明：

EmptyDir

  • 描述：EmptyDir 是 Kubernetes 中的一种卷，它在 Pod 中创建一个空目录，供容器使用。
  • 生命周期：EmptyDir 的生命周期与 Pod 绑定。当 Pod 被删除或重新启动时，EmptyDir 中的内容会被清空，因此它不是持久化存储解决方案。
  • 应用场景：适用于需要在 Pod 内部多个容器之间共享临时数据的场景，或者用于存储短期数据，如缓存或中间结果。

hostPath

  • 描述：hostPath 卷将容器的某个目录挂载到宿主机的文件系统路径。它使得容器能够访问宿主机上的文件和目录。
  • 生命周期：hostPath 持久化数据依赖于宿主机，但它并不适用于跨节点的集群环境。
  • 应用场景：适用于需要直接访问宿主机文件系统的场景，如日志存储、容器监控等。

NFS

  • 描述：NFS（网络文件系统）卷通过网络挂载远程服务器上的共享目录，容器可以像访问本地文件一样访问它。
  • 生命周期：NFS 提供持久化存储，且可以跨 Pod 和节点共享数据。
  • 应用场景：适用于跨多个节点共享数据的场景，尤其是需要共享数据且要求高可用的应用。

persistentVolumeClaim (PVC)

  • 描述：PVC 是用于申请持久化存储的一种声明。在 Kubernetes 中，管理员可以预先配置一个或多个持久化卷（PV），而用户则通过 PVC 申请使用这些卷。
  • 生命周期：PVC 提供持久化存储，能够跨 Pod 和节点存活。它可以与 PV 绑定，从而提供稳定的存储空间。
  • 应用场景：适用于需要持久化存储的应用，如数据库、日志文件存储等。

GlusterFS

  • 描述：GlusterFS 是一个分布式文件系统，允许在多个服务器之间创建一个共享存储池。Kubernetes 中的 GlusterFS 卷使得多个 Pod 可以访问同一个存储池。
  • 生命周期：提供跨节点的持久化存储，并且支持容器和节点间的共享。
  • 应用场景：适用于需要高可用、跨节点共享数据的场景，特别是当应用需要分布式存储时。

CephFS

  • 描述：CephFS 是一个分布式文件系统，基于 Ceph 存储系统。它提供高性能、可扩展的共享存储解决方案。
  • 生命周期：CephFS 支持跨多个 Pod 和节点共享数据，适用于需要高可用和高性能的应用。
  • 应用场景：适用于需要大规模分布式存储和跨节点共享存储的场景。

ConfigMap

  • 描述：ConfigMap 是 Kubernetes 中的一个对象，用于存储非敏感的配置信息。可以将这些配置信息挂载到 Pod 中，供容器访问。
  • 生命周期：ConfigMap 数据存储在 Kubernetes 集群中，可以在多个 Pod 中共享，但它本身并不是持久化存储。
  • 应用场景：适用于存储配置信息，尤其是应用程序需要动态加载的配置文件。

Secret

  • 描述：Secret 用于存储敏感数据（如密码、API 密钥等）。与 ConfigMap 类似，Secret 可以挂载到容器中，但其数据经过编码或加密，以防止泄露。
  • 生命周期：Secret 数据存储在 Kubernetes 集群中，并可以跨多个 Pod 共享，但它本身并不是持久化存储。
  • 应用场景：适用于存储应用的敏感信息，确保敏感数据的安全。

不同的卷使用场景：

  • EmptyDir：临时存储，不适合持久化数据。
  • hostPath：适用于与宿主机文件系统交互的场景，但无法跨节点共享。
  • NFS、GlusterFS、CephFS：适用于跨节点共享数据的场景，提供持久化存储。
  • PVC：适合持久化存储和跨节点共享，适用于数据库等有状态应用。
  • ConfigMap、Secret：适用于存储配置文件和敏感信息，能够在容器间共享数据，但不用于存储大量数据。

根据不同的需求和场景，可以选择合适的卷类型来管理 Kubernetes 中的数据存储。

EmptyDir 卷的使用场景

EmptyDir 是 Kubernetes 中的一种临时存储解决方案，它为容器提供一个空目录，并在 Pod 的生命周期内可用。以下是 EmptyDir 卷的常见使用场景：

  1. 临时文件共享
    如果多个容器需要在同一个 Pod 中共享临时文件，EmptyDir 卷是一个简单有效的解决方案。容器可以将数据写入 EmptyDir 卷，其他容器可以访问并修改这些数据。当 Pod 被删除或重新启动时，EmptyDir 中的所有数据都会丢失。
  2. 共享数据
    有时，多个容器可能需要访问相同的数据或中间结果。EmptyDir 可以作为容器间的临时数据交换机制。例如，一个容器可以将处理结果存入 EmptyDir，另一个容器则可以读取并处理这些数据，从而实现数据共享。
  3. 缓存
    EmptyDir 卷非常适合用作容器的缓存存储。某些应用程序需要将频繁访问的数据缓存到本地存储中，以提高性能。EmptyDir 提供了一个临时、高速的存储介质，能快速存取数据并提升应用性能。

Kubernetes 中使用存储卷的步骤

在 Kubernetes 中使用存储卷时，一般需要遵循以下步骤：

  1. 定义 Pod 的 Volume
    在 Pod 的配置文件中定义一个 Volume，指定它要关联的存储类型（例如 EmptyDir、HostPath、PersistentVolumeClaim 等）。每种存储类型适用于不同的需求。例如，EmptyDir 用于临时数据存储，而 PersistentVolumeClaim 用于持久化数据存储。
  2. 在容器中使用 Volume Mounts
    在 Pod 配置中，为每个容器定义 volumeMounts，并指定将 Volume 挂载到容器内的路径。这使得容器能够访问和操作该 Volume 中的数据。例如，容器可以将应用日志或缓存数据写入到挂载的 Volume。
  3. 实现数据持久化和共享
    一旦 Volume 被挂载到容器中，容器可以在 Volume 中写入数据或从中读取数据。通过这种方式，数据可以在容器的生命周期内持久化，并且可以被同一 Pod 中的其他容器共享或访问。例如，Pod 中的多个容器可以通过同一个 EmptyDir 卷共享缓存数据或临时文件。

总结

  • EmptyDir 卷适用于在同一 Pod 中的容器间共享临时数据、缓存数据以及中间处理结果，但不提供持久化存储。
  • 在 Kubernetes 中使用存储卷时，需要定义 Volume、配置 volumeMounts，并确保容器能够正确访问和操作挂载的 Volume。

2、 实战：k8s持久化存储方案-hostPath

hostPath 卷在 Kubernetes 中的使用

hostPath 是 Kubernetes 中的一种卷类型，它允许容器访问并挂载宿主机节点上的特定文件或目录。通过 hostPath，容器可以直接与宿主机的文件系统交互，这对于某些特定场景非常有用，但也伴随一些潜在的风险和限制。

hostPath 卷的关键特点与适用场景：

1.直接访问主机文件系统

  • 特点：hostPath 允许容器直接访问宿主机节点上的文件系统路径。这对于需要从宿主机读取特定文件或目录的应用程序非常有用。例如，日志收集器或监控代理可能需要访问宿主机的日志文件或配置文件。
  • 应用场景：适用于需要直接读取或写入宿主机文件系统数据的场景，如日志处理、调试等。

2.主机依赖性

  • 特点：hostPath 卷与宿主机节点紧密绑定，因此如果 Pod 被调度到另一个节点，容器将无法访问之前挂载的宿主机文件系统。这会导致跨节点的访问不可靠。
  • 应用场景：在选择 hostPath 时，必须确保 Pod 被调度到正确的节点，或者只适用于某些特定的静态节点。此限制在 Kubernetes 的调度过程中需要特别关注。

3.风险和潜在问题

  • 特点：hostPath 卷的使用需要谨慎，因为容器可以访问宿主机上任何文件或目录，包括敏感的系统文件。如果多个 Pod 同时访问相同的 hostPath 卷并且进行写操作，可能会导致文件冲突或数据损坏。
  • 应用场景：如果必须使用 hostPath，应避免并发写操作，并确保卷的访问权限受到严格控制。此外，避免将敏感或关键系统文件挂载到容器中。

4.开发和测试环境

  • 特点：由于 hostPath 卷允许快速将宿主机上的文件映射到容器中，它非常适用于开发和测试环境。在这些环境中，开发者可以轻松地将宿主机的数据、配置或日志文件挂载到容器中，从而加速开发和调试过程。
  • 应用场景：适用于开发和测试阶段，尤其是当需要容器访问宿主机数据时，如日志分析、配置测试等。

生产环境中的使用限制

虽然 hostPath 卷在开发和测试环境中有一定优势，但它并不适合生产环境中的大多数用例。主要原因在于：

  • 宿主机依赖性：生产环境通常需要高可用性，hostPath 的节点绑定特性使得它不适合用于需要跨节点访问的场景。
  • 风险和不稳定性：hostPath 的风险较高，容器可能会不小心访问到敏感的系统文件或出现数据冲突，导致潜在的安全隐患和稳定性问题。

生产环境推荐的替代方案

在生产环境中，建议使用更可靠的存储解决方案，如：

  • 网络存储（NFS）：可以跨多个节点共享存储，适合需要多节点访问相同数据的场景。
  • 云存储服务：例如 AWS EBS、Google Cloud Persistent Disk 等，提供可靠、可扩展的存储解决方案。
  • 对象存储：如 S3，适合大规模的非结构化数据存储。

总结

  • hostPath 卷适用于开发和测试环境，特别是当需要将宿主机数据直接映射到容器时。
  • 在生产环境中，应避免使用 hostPath，并选择更为灵活、可靠的存储方案，如 NFS、云存储或对象存储。
  • 使用 hostPath 时，需要特别注意宿主机节点的依赖性以及对敏感数据和文件的访问控制。

hostPath 存储卷的缺点

hostPath 是 Kubernetes 中的一种存储卷类型，它将宿主机上的文件或目录挂载到容器内。尽管它在一些场景下非常有用，但它有一些限制和缺点：

  1. 单节点依赖
    hostPath 卷是与特定的节点绑定的，因此它只能在 Pod 所在的同一节点上访问。如果 Pod 被调度到另一个节点，之前挂载的 hostPath 卷将无法访问，导致数据丢失或不可用。
  2. Pod 删除后数据丢失
    当使用 hostPath 卷时，Pod 被删除并重新创建时，必须将 Pod 调度到相同的节点，否则它将无法访问之前挂载的 hostPath 卷。这个特性让 hostPath 卷在需要跨节点调度的场景下变得不适用。

3、 实战：k8s持久化存储方案-NFS

NFS（Network File System）在 Kubernetes 中的应用

NFS 是一种网络文件系统协议，它允许不同计算机通过网络共享文件和目录。NFS 可以作为 Kubernetes 中的一种持久化存储解决方案，适用于需要跨多个节点共享数据的应用场景。下面是 NFS 的一些基本介绍和常见应用场景：

NFS 的基本原理

  1. 存储共享
    NFS 允许将存储资源（文件或目录）通过网络共享给其他计算机。NFS 服务器将存储资源公开为共享，并通过网络将其挂载到客户端上，客户端可以像访问本地文件系统一样访问这些共享资源。
  2. 持久化存储方案
    在 Kubernetes 中，NFS 可以作为持久化存储方案使用。它为容器提供可靠的存储，确保即使容器被调度到不同的节点时，数据仍然保持一致性。相比 hostPath，NFS 适合跨多个节点访问数据。

NFS 的应用场景

  1. 分布式访问
    NFS 允许多个客户端（例如多个 Pod 或容器）同时访问同一共享资源，这使得它特别适用于需要多个容器共享数据的场景。例如，数据库系统或日志收集系统等需要共享存储的应用。
  2. 跨平台兼容性
    NFS 是一种跨平台的协议，支持在不同操作系统之间进行文件共享。因此，NFS 适用于混合操作系统集群中的持久化存储场景，例如在 Linux 和 Windows 系统间共享数据。
  3. 灵活性
    NFS 提供灵活的存储访问和管理功能，管理员可以根据需要创建和配置 NFS 服务器，控制访问权限，并实施访问控制策略。通过设置 NFS 服务的权限，确保安全性。
  4. 备份和恢复
    NFS 支持数据备份和恢复功能，管理员可以使用备份工具对共享的 NFS 数据进行定期备份，以防止数据丢失或损坏。这使得 NFS 成为备份恢复策略中的重要一环。

总结

  • hostPath 卷适用于单节点环境，但由于其主机依赖性和容器删除后的数据丢失问题，hostPath 并不适合跨节点的数据存储需求。
  • NFS 提供了更强大的跨节点数据共享和持久化存储能力，适合需要跨多个节点访问共享数据的应用场景，且具备备份、恢复和跨平台兼容等优势。

在生产环境中，建议使用 NFS 或其他分布式存储解决方案，以确保数据的高可用性和一致性，避免使用 hostPath 的局限性。

4、 k8s持久化存储方案-PVC

PV（PersistentVolume）和 PVC（PersistentVolumeClaim）概述

在 Kubernetes 中，PersistentVolume（PV） 和 PersistentVolumeClaim（PVC） 是用来管理持久化存储资源的核心对象。它们为 Pod 提供了持久化存储，确保即使 Pod 被删除，存储中的数据依然保留。

什么是 PersistentVolume（PV）？

PV 是集群中的一个存储资源，通常指物理存储设备、网络存储（如 NFS 或 Ceph）或云存储等。PV 是集群级别的资源，由集群管理员进行配置和管理。每个 PV 都有持久性，即使 Pod 被删除，存储中的数据也不会丢失。PV 具有以下几个特点：

  • 存储容量：指定 PV 提供的存储空间大小。
  • 访问模式：例如，ReadWriteOnce（单节点读写）、ReadOnlyMany（多个节点只读）、ReadWriteMany（多个节点读写）等。
  • 回收策略：例如保留（Retain）、删除（Delete）或回收（Recycle）。

什么是 PersistentVolumeClaim（PVC）？

PVC 是 Pod 向 Kubernetes 请求存储资源的方式，它是对 PV 的申请。PVC 定义了 Pod 对存储的需求，包括存储容量和访问模式等。PVC 使得 Pod 无需了解底层存储的具体细节，只需要声明所需的存储要求即可，Kubernetes 会自动将其与合适的 PV 绑定。PVC 提供了以下功能：

  • 存储需求声明：例如指定存储的大小和访问模式。
  • 与 PV 绑定：PVC 创建后，Kubernetes 会自动找到符合要求的 PV，并将其与 PVC 绑定。

PV 和 PVC 的工作原理

  1. PV 的供应方式：
    • 静态配置：由管理员预先创建 PV 对象，包含了实际存储资源的详细信息，这些 PV 由用户申请。
    • 动态配置：当没有合适的静态 PV 时，Kubernetes 可以根据 PVC 的要求动态创建一个 PV。为此，管理员需要配置 StorageClass，PVC 会请求特定的 StorageClass 来自动配置 PV。
  2. PVC 的绑定：
    • 用户创建 PVC，并指定所需的存储资源和访问模式。
    • PVC 会进入未绑定状态，直到有合适的 PV 可以匹配 PVC 的要求。
    • 绑定关系：PV 和 PVC 是一对一的关系，一旦 PV 被绑定到 PVC 上，其他 PVC 就无法再使用该 PV。
  3. PVC 的使用：
    • 用户在创建 Pod 时，指定 PVC 作为存储卷挂载到容器中。
    • 一旦 PV 与 PVC 绑定，Pod 就可以使用 PVC 所申请的存储卷来保存数据。
  4. PV 的回收策略：
    • Retain（保留）：删除 PVC 后，PV 保留并且数据不被删除。PV 不会绑定到其他 PVC，可以重新使用。
    • Delete（删除）：删除 PVC 后，PV 也会被删除，并且相应的存储资源也会被释放。
    • Recycle（回收）：删除 PVC 后，PV 会被清空并准备重新使用（Kubernetes 1.15 以后不推荐使用该回收策略）。

总结

Kubernetes 的 PV 和 PVC 提供了灵活且可扩展的存储管理方式。PV 作为集群级别的持久化存储资源，为 Pods 提供可靠的存储，PVC 则使 Pods 可以声明和请求存储资源，避免了对底层存储实现的直接依赖。通过这种机制，Kubernetes 实现了存储资源的动态管理和灵活使用。通过不同的回收策略，Kubernetes 还可以灵活地管理存储资源的生命周期。

5、 k8s存储类：StorageClass

Kubernetes 为了降低持久化存储的运维复杂度，引入了 StorageClass 机制，用于实现 PV 的自动、动态创建。在传统的 PV / PVC 使用模式中，集群管理员需要提前手动创建 PersistentVolume（PV），用户再通过 PersistentVolumeClaim（PVC）进行一对一绑定，这种方式在集群规模较大时会带来较高的管理和维护成本。

StorageClass 本质上是一个 动态创建 PV 的模板，由管理员预先定义好存储类型、参数和策略等信息。当用户创建 PVC 并指定某个 StorageClass 时，Kubernetes 会根据该 StorageClass 的定义自动创建一个符合要求的 PV，并立即与 PVC 绑定，从而实现存储资源的按需分配。

通过 StorageClass，可以显著简化存储管理流程，避免手工维护大量 PV；同时支持动态供应，提高资源利用率；并且允许管理员根据不同性能、访问模式或存储后端创建多个 StorageClass，用户只需选择合适的 StorageClass 即可获得对应的存储能力，从而实现存储使用上的灵活性和标准化。

在 Kubernetes 中，StorageClass 需要指定一个 provisioner（供应者），用于明确由哪一种存储后端来动态创建 PersistentVolume（PV）。provisioner 本质上就是存储驱动，它决定了 PV 实际使用的存储类型，例如云厂商的块存储、NFS、Ceph 等。不同的 provisioner 对应不同的存储实现方式，常见的 provisioner 可以参考 Kubernetes 官方文档中 StorageClass 的说明。

另外，StorageClass 还支持通过 allowVolumeExpansion 字段来控制是否允许卷扩展。当该字段设置为 true 时，表示基于该 StorageClass 创建的 PV 支持在线或离线扩容。用户可以通过直接修改对应的 PVC 对象中的存储容量请求，来触发卷的扩展操作。前提是底层存储系统本身支持扩容能力，否则即使开启了 allowVolumeExpansion，扩容也无法生效。通过这一机制，Kubernetes 可以在不重新创建 Pod 的情况下，灵活调整持久化存储的容量，更好地满足业务增长需求。

扩展

ServiceAccount（SA） 的全称是 serviceaccount，它是 Kubernetes 中用于 身份认证和权限控制 的一种资源对象，主要目的是方便 Pod 内部的进程访问 Kubernetes API 或其他需要鉴权的外部服务。每个 ServiceAccount 都可以绑定对应的 RBAC 权限规则，从而明确该 Pod 在集群中“能做什么、不能做什么”。当在 Pod 的配置中显式指定了某个 ServiceAccount 后，Pod 创建完成后，Pod 内的容器就会自动使用该 ServiceAccount 的身份和权限运行，相当于为 Pod 分配了一个专属的“访问凭证”。如果不指定，Pod 默认会使用所在命名空间下的 default ServiceAccount。

在存储相关的配置中，需要特别注意 StorageClass 的回收策略（reclaimPolicy）。StorageClass 默认使用的回收策略是 Delete，这意味着当 PVC 被删除时，不仅 PVC 本身会被删除，与之绑定的 PV 也会被一并删除，同时底层真实存储资源（例如云磁盘、NFS 目录等）中的数据也会被清理。这种行为在生产环境中具有较高风险，可能导致重要数据被误删。

因此，在生产环境中通常建议将回收策略设置为 Retain。在 Retain 策略下，当 PVC 被删除时，PV 及其对应的后端存储数据都会被保留下来，管理员可以在确认数据安全的前提下，再手动处理或重新绑定该 PV，从而有效避免因误操作造成的数据丢失。这也是 Kubernetes 官方文档中推荐的生产环境实践方式之一。
