Kubernetes四层代理Service-使用技巧和应用场景

1、 四层负载均衡Service基本介绍

​ 在 Kubernetes 中，**四层代理（Layer 4 Proxy）**是指工作在传输层（TCP/UDP）的代理机制，它并不关心具体的应用协议内容，而是根据 IP 地址和端口将网络请求从客户端转发到后端目标。在 Kubernetes 里，Service 正是四层代理的一种典型实现，用于完成服务的负载均衡和服务发现。

​ Service 是 Kubernetes 中的一个资源对象，它通过标签选择器将一组具有相同标签的 Pod 组织成一个逻辑整体，并为这组 Pod 分配一个稳定的虚拟 IP，即 ClusterIP。客户端只需要访问这个虚拟 IP，就可以透明地访问后端 Pod，而无需感知 Pod 的具体数量和变化情况。

以下是Service的基本介绍：

  • Cluster IP：每个 Service 都会自动分配一个 ClusterIP，该 IP 仅在集群内部可访问，用于集群内服务之间的通信。

  • 端口映射：Service 支持端口映射机制，客户端访问 Service 的某个端口时，请求会被转发到后端 Pod 对应的容器端口。

  • 负载均衡：Service 基于四层代理机制实现负载均衡，当一个 Service 后面关联了多个 Pod 时，请求会被自动分发到当前可用的 Pod 上。

  • DNS解析：Kubernetes 还会将 Service 自动注册到集群内置的 DNS 系统中，客户端可以直接通过服务名称进行访问，而无需记忆具体的 ClusterIP 地址。

Service与pod之间的关系

​ Service 与 Pod 之间并不是直接绑定的，而是通过 标签选择器和 Endpoint 对象建立联系。在创建 Service 时，Kubernetes 会根据 Label Selector 筛选符合条件的 Pod，并自动生成与 Service 同名的 Endpoint 对象。Endpoint 中记录了当前可用 Pod 的 IP 和端口信息。当客户端请求到达 Service 的虚拟 IP 时，kube-proxy 会查找对应的 Endpoint 列表，并按照一定的负载均衡策略（如轮询）选择一个 Pod，将请求转发过去。在使用 IPVS 模式时，这一转发过程会通过内核中的 IPVS 规则完成，查询效率高、性能稳定。

为什么不直接请求Pod的ip?而是要创建Service?

​ 之所以不直接访问 Pod IP，而是要通过 Service 进行访问，根本原因在于 Pod 的 生命周期不稳定。Pod 在升级镜像、重建或调度到其他节点时，其 IP 地址通常会发生变化，如果客户端直接依赖 Pod IP，就会导致访问中断。而 Service 提供了一个稳定不变的访问入口，即使后端 Pod 发生变化，客户端的访问方式也无需调整。这种设计实现了对后端变化的屏蔽，提高了系统的可用性和可维护性。

Kubernetes集群中的 ip地址

在 Kubernetes 集群中，IP 地址主要分为三类Pod IP、Service ClusterIP 和 Node IP。

  • Pod IP ：分配给每个 Pod 的内部 IP，用于 Pod 之间的直接通信；

  • Service ClusterIP ：分配给 Service 的虚拟 IP，用于在集群内部作为服务访问入口；

  • Node IP ：节点本身的 IP 地址，用于集群节点之间以及集群与外部网络之间的通信。在使用 kubeadm 部署集群时，需要特别注意 serviceSubnet（如 10.96.0.0/12）和 podSubnet（如 10.244.0.0/12）这两个网段不能发生冲突，否则集群初始化会失败。

​ 这三类 IP 在集群中各司其职：Pod IP 实现容器之间的网络互通，Service ClusterIP 提供稳定的服务访问入口，而 Node IP 则承担对外通信和节点管理的角色。正是通过 Service 这一抽象层，Kubernetes 才实现了对 Pod 动态变化的屏蔽，从而为上层应用提供了稳定、透明且可扩展的服务访问方式。

2、 创建Service资源

通过kubectl explain查看定义Service资源需要哪些字段

​ Service 的配置字段用于控制服务的访问方式和流量行为。其中，type 用于指定 Service 的类型，常见取值包括 ClusterIP、NodePort、LoadBalancer 和 ExternalName。

  • allocateLoadBalancerNodePorts：用于控制 LoadBalancer 类型的 Service 是否自动分配 NodePort。

  • clusterlP：表示 Service 在集群内部使用的虚拟 IP，通常由系统自动分配。

  • clusterlPs：用于支持多个 ClusterIP，常见于双栈场景。

  • externalIPs：用于将 Service 通过指定的外部 IP 暴露到集群外。

  • externalName：用于将 Service 映射到一个外部 DNS 名称，本身不创建 ClusterIP。

  • externalTrafficPolicy：用于控制外部流量的转发策略，取值为 Cluster 时会在全集群范围内负载均衡，取值为 Local 时仅转发到本节点上的 Pod，并保留客户端真实 IP。

  • healthCheckNodePort： 表示负载均衡器进行健康检查时使用的节点端口。

  • ipFamilies：用于定义 Service 支持的 IP 地址族及其策略，和ipFamilyPolicy一起使用的，例如单栈或双栈。

  • loadBalancerlP：用于指定负载均衡器使用的固定 IP。

  • loadBalancerSourceRanges： 用于限制可访问负载均衡器的源 IP 范围。

  • ports：用于定义 Service 对外暴露的端口及其与后端 Pod 端口的映射关系。

  • publishNotReadyAddresses：表示是否将尚未就绪的 Pod 地址也加入 Service，常用于 StatefulSet 等特殊场景。

  • selector：标签选择器，用于关联后端 Pod；如果不设置 selector，Service 通常需要手动维护 Endpoint。

  • sessionAffinity：用于控制会话亲和性策略，支持 None 和 ClientIP。

  • sessionAffinityConfig：可进一步配置sessionAffinity参数。

  • topologyKeys：用于启用服务的拓扑感知能力，使流量优先转发到符合拓扑条件的后端 Pod。

Kubernetes Service 用于为一组 Pod 提供稳定的访问入口，其类型决定了服务的访问方式与适用场景。

ClusterIP：ClusterIP 是默认的 Service 类型，系统会为 Service 分配一个虚拟的 ClusterIP，仅能在集群内部访问，适用于集群内服务发现与通信。

NodePort：NodePort 类型会在每个节点上开放一个固定端口，并将该端口映射到 Service，对外部用户可通过 NodeIP 加 NodePort 的方式访问服务，适合需要从集群外部直接访问的场景。

LoadBalancer：LoadBalancer 类型依赖云服务提供商创建外部负载均衡器，并自动分配公网 IP，将外部流量分发至后端 Pod，适用于对高可用性和负载均衡有要求的业务。

ExternalName：ExternalName 类型则不分配 ClusterIP 或 NodePort，而是将 Service 映射到一个外部 DNS 名称，当集群内部访问该 Service 时，DNS 会直接解析为外部服务地址，常用于与集群外系统进行集成。

​ 根据应用需求和场景，选择适当的Service类型可以实现不同的访问方式和网络架构。例如，如果需要在集群内部实现服务发现和访问，可以使用ClusterlP；如果需要从集群外部访问Service，可以选择NodePort；如果需要高可用性和负载均衡，可以使用LoadBalancer；如果需要将Service与外部服务集成，可以使用ExternalName。根据具体的业务需求，可以灵活选择合适的Service类型。在端口配置方面：

  • targetPort 为必需字段，用于指定流量最终转发到 Pod 容器的端口号或端口名称。

  • nodePort 仅在 NodePort 类型中使用，可手动指定或由系统自动分配。

​ 通过在 spec.ports 中定义端口映射关系，Service 能够将请求转发到多个后端 Pod，实现负载均衡与服务发现。根据业务访问范围、网络架构及可用性需求，合理选择 Service 类型可以有效提升系统的稳定性与可维护性。
